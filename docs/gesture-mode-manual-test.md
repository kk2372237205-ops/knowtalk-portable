# 手势模式 · 人工验收清单

状态：待执行 · 最后核对日期：2026-10-14

自动化已经覆盖的部分不在这里重复。本清单只列**必须在真实浏览器 + 真实 WebRTC 会话里走一遍**的项，
对应 `openspec/changes/add-gesture-module/tasks.md` 的 6.2。

> 为什么要人工：这些验收依赖真实 WebRTC 会话与数字人画面，单元测试用的是假 ASR 队列与替身帧源，
> 能覆盖"索引是否从 0 开始""播满一遍是否回默认"，但覆盖不到"画面上看起来像不像在做动作"。

---

## 0. 前置准备

```bash
# 启动（端口 8010）
python app.py --transport webrtc --model wav2lip --avatar_id Mr.Chen
# 或用 start.bat
```

1. 确认素材已就位（三件套齐备才会出现在可用列表里）：

   ```bash
   curl "http://127.0.0.1:8010/api/avatars/Mr.Chen/gestures"
   # 期望：{"code":0,...,"data":{"gestures":[{"id":"explain","label":"讲解手势"}]}}
   ```

2. 浏览器打开 <http://127.0.0.1:8010>，点「开始连接」，记下页面上的 **SID**。
3. 在「预设文本」区确认**插入手势**一行出现了「讲解手势」按钮；点它应在文本框光标处插入 `[GESTURE:explain] `。

**全程用这个命令观察当前幻灯片**（用于确认切页时机没被手势改动）：

```bash
curl "http://127.0.0.1:8010/api/current_slide?sessionid=<SID>"
```

## T1 · 无手势讲稿回归（任务 6.2）

**目的**：不含手势标签时，行为必须与引入手势前完全一致。

- [ ] 讲稿只写 `[PPT:N]` 标签（4～5 段），点「播报预设文本」
- [ ] 说话、切页、静音画面全程正常，**没有任何动作变化**
- [ ] 记录 `/api/current_slide` 的取值序列，与改动前（或与 T1 基线）一致
- [ ] 讲稿里**不要**出现 `[GESTURE:` 字样，且页面按钮没有被误点

**判定**：与改动前一致——画面全程是默认素材循环，切页时机不变。

---

## T2 · 手势触发与"只播一遍"（任务 6.2）

**目的**：手势能触发、播完自动回默认、朗读不断流。

- [ ] 讲稿写成：`[PPT:1] 第一段没有动作。[GESTURE:explain] 第二段我用手势说明。[PPT:2] 第三段回到默认。`
- [ ] 播报后观察：念到**第二段开头**时画面切到手势素材（双手抬起比划）
- [ ] 手势**只完整播一遍**（约 5 秒，121 帧 @25fps），随后画面回到默认姿态（双手垂下）继续循环
- [ ] 第二段的朗读**没有**被截断、**没有**插入静音，语速不受影响
- [ ] 第三段画面是默认素材，**没有**再次触发手势（验证"不跨段继承"）
- [ ] 记录：切页时机与 T1 一致

**判定**：动作出现在第二段段首，播完回默认，语音时间线无变化。若第二段比手势短，
手势仍应播满一遍再回默认，而不是中途被切掉。

## T3 · 边说边做（任务 6.2）

**目的**：手势期间嘴型仍由语音实时驱动，不是整帧直接输出素材。

- [ ] 在 T2 的同一遍里，仔细看手势播放期间的**嘴部**：应随朗读开合，而不是素材里那张静止的嘴
- [ ] 观察**输出画面尺寸**（WebRTC 视频轨分辨率）在切换前后**没有变化**——不应出现编码器重建导致的短暂花屏
- [ ] 手势期间若出现静音段（句间停顿），画面应继续推进手势帧序，而不是卡住

**判定**：嘴边说话边动，分辨率恒定，无花屏。

---

## T4 · 循环接缝与首尾姿态（任务 6.2）

**目的**：素材首尾姿态接近时不应有可见跳变。

- [ ] 让数字人**静音**时观察默认素材循环一段（手势播完之后的常态）
- [ ] 再触发一次手势（把 T2 讲稿再发一遍），观察**切换瞬间**是否有明显跳变
- [ ] 记录跳变程度：无 / 轻微 / 明显（明显时说明素材首尾姿态差得远）

**判定**：切换处至多"轻微"。首版没有交叉淡入，这是已知取舍；若明显，需要换素材而不是改代码。

## T5 · 错误提示与受理拦截（任务 6.2）

**目的**：写错手势名不会静默失效，也不会把整篇讲稿拒掉。

> 2026-10-26 起口径是「只摘除、不整篇报错」：引用了该形象没有的手势，那段照常朗读，
> 只是不播动作，并在响应的 `data.warnings` 里说明。

- [ ] 讲稿写 `[PPT:1] 第一段。[GESTURE:nosuch] 第二段。`，播报
- [ ] 响应 `code` 为 0，`data.warnings` 里同时出现 `nosuch` 与该形象的可用手势名
- [ ] 数字人**照常把两段都读完**（不是静默跳过整篇）
- [ ] 页面上出现黄色提示条（`#statusBanner`），不是一个一闪而过的 toast

**判定**：warning 可定位到具体手势名，朗读不中断。

## T6 · 多手势与缓存（任务 6.2）

**目的**：缓存命中不重复读盘，切换形象时按钮跟着变。

> 这一项需要第二套手势素材（例如 `wave`）才能完整走。只有一套素材时跳过子项。

- [ ] 讲稿交替使用同一手势 3 次以上 → 第 2 次起触发**明显更快**（命中缓存，不再读盘）
- [ ] 在「Avatar ID」下拉里切到另一个形象 → 手势按钮区刷新为该形象的手势（没有手势时显示提示文案）
- [ ] 切回 `Mr.Chen` → 按钮恢复
- [ ] 会话结束（断开连接或等待空闲回收）后进程日志里出现会话资源释放的记录，且内存没有持续上涨

**判定**：缓存生效、按钮随形象刷新、会话释放有记录。

## T7 · 动作按原速播放（任务 4.6 / 7.5）

**目的**：动作不会因为输出帧率低于素材帧率而变成慢动作。

> 素材是 24fps 出片（107 帧 ≈ 4.46 秒），`musetalk` 默认输出 20fps。旧行为是"每输出一帧
> 前进一帧"，同一段动作要播 5.35 秒（慢 20%）；现在按输出帧率重采样成 89 帧。

- [ ] 用 `docs/课程脚本-精简带动作.txt` 完整讲一遍（9 次动作、6 个手势 id）
- [ ] 每次动作从起手到"回到体侧"约 4.5 秒，与素材观感一致（不是明显拖慢）
- [ ] 动作期间口型照常跟随语音，动作结束时画面平滑回到基础素材
- [ ] 日志出现 `[手势] <id> 按 24→20 fps 重采样到输出帧率：89 帧`
- [ ] `data/avatars/musetalk_ke/gestures/*/gesture.json` 均含 `"fps": 24`

**判定**：动作节奏自然、时长与素材一致；日志确认走了重采样。

## T8 · 动作播放不卡顿（任务 8.6）

**目的**：讲课时不应该出现"动作一顿一顿"或"动作出现前先卡半秒"。

> 历史成因（2026-10-27 修）：讲稿有 6 套动作但缓存只留 2 套 → 讲到中间反复淘汰重载；
> 讲到第 3 个动作才现读盘 → 触发到真正切换晚 1.9 秒；推理约 18.6fps 而输出 20fps，
> 缺帧时画面被冻结 → 手臂周期性停顿。

- [ ] 启动服务后看日志：受理讲稿时出现 `[手势] 开始预热 6 套动作：count, press, ...`
      （讲稿用到的全部动作，而不是只有前两套）
- [ ] 讲完整篇（9 次动作）：**不应**再出现 `[手势] 缓存已满，淘汰最久未使用的手势`
- [ ] 每 200 帧出现一条 `[平滑] 近 200 帧中补帧 N 帧（x%）`；补帧率应在 0~10% 量级
- [ ] 每个动作起手时画面平滑进入，**没有**"先停半秒再开始"或"手臂一卡一卡"
- [ ] 动作期间嘴仍在动，且**没有**闭合闪跳
- [ ] 任务管理器里服务进程内存：讲完整篇后应基本持平（不再随动作数量线性上涨）

**判定**：全程无明显停顿；日志里没有淘汰记录、补帧率低；内存平稳。

## T9 · 动作收尾不卡（任务 9.8）

**目的**：每个动作**快结束**的那一两秒不能顿一下、也不能"突然收回去"。

> 历史成因（2026-10-27 修）：默认形象只有 1 帧、动作素材 89 帧。动作播完切回默认素材时，
> 队列里还压着十几个带手势索引的在途帧，贴回步骤用裸下标 → **逐帧越界**；异常被吞掉后
> 这一帧的视频和音频一起被丢弃 → 接收端欠载。日志实证：
>
> ```
> [手势] count 已完整播放一遍（89 帧），回到默认素材
> paste_back_frame error: list index out of range    × 16
> audio queue underrun: count=1, queued=0            × 数十条
> ```
>
> 另外进度原先由推理线程按批量产出推进，比画面超前 → 切换早于末帧动作真正播出。

- [ ] 启动服务后讲完整篇，日志里**没有任何**一条
      `paste_back_frame error: list index out of range`
- [ ] 每个动作结尾：手臂是**自然放回体侧**的完整收尾，不是中途被切掉、也不是"弹"回起始姿势
- [ ] 观察 3 个以上不同动作的收尾，都**没有**"动作结束后画面停住半拍再跳一下"
- [ ] 动作结束回到默认姿态后，嘴继续跟着语音动，**没有**闭合闪一下
- [ ] 日志里每个动作都出现一次 `… 已完整播放一遍（89 帧），回到默认素材`，
      时间戳与触发时刻相差约 **4.4 秒**（89 帧 @20fps；明显短于 4 秒说明被提前切掉了）
- [ ] 动作收尾前后不应出现成片的 `audio queue underrun`（偶发 1~2 条属正常）

**判定**：收尾动作完整播出、无越界报错、无欠载刷屏；动作时长约 4.4 秒。

## T10 · 动作期间脸型/身形与形象一致（任务 8.9）

**目的**：做动作时不能"换一个人"。动作素材是生成出来的视频，脸型会漂移；现在动作只
贡献身体与姿态，人脸参考（latent / 遮罩 / 人脸框）恒取自形象自身，长度 1。

**准备**：先确认 6 套动作的资产都是共享模式（每套只有 1 份）：

```
data/avatars/musetalk_ke/gestures/<id>/musetalk/asset.json   → {"mode": "shared", ...}
data/avatars/musetalk_ke/gestures/<id>/musetalk/mask/        → 只有 00000000.png
```

> 升级前生成的是**逐帧**资产（每帧一份 latent + 遮罩）。这类旧资产会被判为未就绪；
> 调一次 `POST /api/avatars/musetalk_ke/gestures/<id>/prepare` 即可自动迁移。

- [ ] 静止（不说话、不做动作）时截一张脸
- [ ] 播放 `docs/课程脚本-精简带动作.txt`，在每个动作**进行中**各截一张脸
- [ ] 逐张对比：动作帧与静止帧的**脸型**应一致——脸的宽度、下颌线、颧骨位置都不变
      （改前：动作期间脸明显变宽、更圆，像"胖了一圈"）
- [ ] 动作开始/进行中/结束三个时刻的脸型彼此一致，不随动作帧变化
- [ ] 脸部边缘**没有**双轮廓或残影（说明遮罩覆盖完整）
- [ ] 脖子与下颌衔接处**没有**明显硬边
- [ ] 6 个动作全部检查一遍，结论一致
- [ ] 日志没有 `MuseTalk 资产为空 / 读取失败` 之类的降级告警

**已知残留**：动作素材的**身体**（衣服宽松度、肩线）与形象仍有生成模型带来的轻微差异，
这是素材本身的特性，代码无法修正；若要求完全一致，需要重出素材并在提示词里更强地约束
"与参考图同一个体型"。脸部已由本项修复。

**判定**：动作全程脸型与静止时一致，无双轮廓、无硬边；残留差异仅限身体且不刺眼。

## T11 · 暂停时嘴必须停住（任务 4.7）

**目的**：暂停是"整个形象静止"，不只是本地静音。此前提问模式自动暂停只切断了本地音轨，
没告诉服务端，于是推理照旧、画面上的嘴一直在动。

> 所有暂停入口现在都走 `setPlaybackPaused()`：本地变量、按钮文案、服务端暂停态一起改。

- [ ] 播放讲稿，点「暂停播放」→ 嘴立刻停住，画面回到默认闭嘴帧
- [ ] 点「继续播放」→ 嘴继续动，从暂停处接着讲，不重播
- [ ] **提问模式**：抛出题目进入「已暂停播放」后，嘴必须停住（这是本次修复的场景）
- [ ] 作答提交后判分反馈能听见，且画面恢复（不是一直定格在默认帧）
- [ ] **动作播放中**暂停：画面回到形象的默认姿态（手臂放下），不是僵在半截动作上
- [ ] 恢复后动作从暂停那一帧继续，不重播整套动作
- [ ] 暂停期间幻灯片不跟着跳页
- [ ] 控制台（F12）不应出现 `[播放] 暂停态同步失败`

**判定**：三种暂停入口（手动 / 提问 / 讲稿）都让嘴停住；恢复后都能继续而不重播。
