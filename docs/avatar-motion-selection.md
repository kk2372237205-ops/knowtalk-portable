## 一、结论先行

### 1.1 三个必须先知道的事实

**【实测】1. 这台机器有 8 GB 独显，此前项目完全没用上；现已换装 CUDA 构建并启用。**

调研时（换装前）的状态：

```
NVIDIA GeForce RTX 4060 Laptop GPU     8188 MiB VRAM
驱动 616.92 / CUDA UMD 13.4
torch 2.14.0+cpu    cuda.is_available() == False    device_count == 0
```

当时安装的 `torch` 是 **CPU-only 构建**（`2.14.0+cpu`），依赖树里没有任何 `nvidia-*` 包，所有推理都在 CPU 上跑，8 GB 显存一直闲置。

**现已换装为 `torch 2.14.0+cu126`**（只换构建变体、不换版本号），实测：

```
cuda.is_available() == True    device_count == 1
total_memory == 8188 MiB（与 nvidia-smi 一致）
wav2lip 前向：CPU 174.4 ms/帧 → CUDA 11.7 ms/帧    加速 14.88×
```

这条数字还有一个更重要的含义：**CPU 上 174 ms/帧 意味着上限约 5.7 fps，本来就达不到 `--fps 25` 的实时要求**；换装后才真正满足实时。详见 `openspec/changes/enable-cuda-runtime/`。

**【实测】2. 画面里本来就有身体，只是它完全静止。**

`data/avatars/Mr.Chen/` 的实际构成：

| 目录 | 帧数 | 单帧尺寸 | 用途 |
|---|---|---|---|
| `full_imgs/` | 150 | **538 × 1080** | 全帧（竖构图，含身体与手） |
| `face_imgs/` | 150 | 256 × 256 | 人脸裁剪，供口型模型推理 |
| `coords.pkl` | — | 1.8 KB | 人脸框坐标 |

现有管线做的是：把 `face_imgs` 送进 wav2lip 改嘴部 → 按 `coords.pkl` 贴回 `full_imgs`。**身体一直都在画面上，只是这 150 帧是一个静止循环**。所以"增加肢体动作"的落点非常明确：**让这 150 帧动起来，或者按内容切换不同的帧序列。**

**【实测】3. 磁盘是真正的硬约束，不是 GPU。**

| 盘 | 可用 | 主要占用 |
|---|---|---|
| C: | 31 GB | Downloads 13.9 GB、.ollama 7.19 GB、Desktop 4.53 GB |
| D: | **6 GB** | Delta Force 130.9 GB、BaiduNetdiskDownload 56.2 GB、UE_5.8 29.9 GB、00-Project 11.4 GB |

CUDA 版 torch 会额外拉入约 2.5 GB 的 `nvidia-*` 依赖（C 盘够）；而任何一个视频生成模型的权重都是 **5–20 GB**（D 盘不够，必须先清理）。

### 1.2 核心取舍：实时性

这一点决定路线选择，必须说清楚。本项目的数字人是**实时交互**形态，不是播放预渲染视频：

| 证据 | 位置 |
|---|---|
| 输出固定 25 fps 的实时流 | `config.py:23` `--fps` 默认 25，注释写明 must be 25 |
| 支持 `chat` 模式实时对话 | `/human` `type=chat` → 流式 LLM → 分段 TTS |
| 支持用户插话打断 | `/interrupt_talk` |
| 三种实时传输方式 | `--transport` webrtc / rtmp / virtualcam |

**【推断】** 扩散式视频生成（EchoMimic V2、InfiniteTalk 等）在 8 GB 笔记本 GPU 上是**秒级到亚秒级每帧**的量级，**达不到 25 fps 实时**。公开资料普遍称这类模型"8G 显存可玩"，但"可玩"指的是**能出片**，不是**能实时对话**。

**因此：扩散式视频生成适合"预生成整节课的视频"，不适合"实时对话数字人"。** 若采用它，产品形态会从"实时数字人"变成"预生成课件视频"，这是一个产品级决策，不只是技术选型。

## 二、三条路线对比

| | A. 真人动作帧序列 | B. 可驱动 2D/3D 角色 | C. 扩散式视频生成 |
|---|---|---|---|
| 形象 | **保留真人** | 变为动画/3D 角色 | 保留真人 |
| 动作来源 | 预录/预剪的帧序列 | **骨骼驱动，可程序化生成** | 模型从音频生成 |
| 动作与语义对应 | 靠配置映射（弱） | **可精确控制**（强） | 强（端到端学习） |
| 实时性 | **25 fps 无压力** | 视渲染方式，通常可实时 | **达不到实时**（推断） |
| 8 GB 显存 | 用不上 | 够 | 勉强，需量化 |
| 磁盘需求 | 几百 MB | 几十 MB + 模型资源 | **5–20 GB** |
| 新增依赖 | 无 | three.js / 渲染器 | CUDA torch + 扩散模型 |
| 主要风险 | 动作固定、拼接跳变 | 形象风格变化、美术资源 | 硬件与磁盘、非实时 |
| 与现有管线 | **复用现有 `customopt` 机制** | 新增并列链路 | 替换整条渲染链路 |

### 2.1 为什么把 A 的"复用现有机制"标为最大优势

**【实测】** 仓库里已经有一套动作播放机制，只是没被用起来：

```
avatars/base_avatar.py:218  def __loadcustom(self):
avatars/base_avatar.py:221      for item in self.opt.customopt:
avatars/base_avatar.py:225          self.custom_img_cycle[item['audiotype']] = read_imgs(input_img_list)
avatars/base_avatar.py:227          self.custom_audio_cycle[item['audiotype']], sample_rate = sf.read(...)
avatars/base_avatar.py:80   self.custom_audiotype = 0   # 0: normal, 1: silence, >1: custom audio
```

它按 `audiotype` 预加载**图片序列 + 音频**，在指定状态下循环播放。这正是"动作片段"需要的机制——**路线 A 主要工作是制作素材与接一个内容→动作的映射，而不是写渲染代码**。

### 2.2 路线 B 的可选实现

**【推断】** 公开可参考的开源实现有两类：

- **VRM + three.js**：如 [svelte-vrm-live](https://github.com/dexvdev/svelte-vrm-live)（Three.js 直播 VRM，含 Mixamo 动画与 TTS 口型）、[Realtime_Avatar_AI_Companion](https://github.com/igna-s/Realtime_Avatar_AI_Companion)（VRM 角色 + 低延迟语音）。VRM 是开放格式，模型可自制或从 VRoid 等平台获取。
- **Live2D**：2D 骨骼，表现力好、资源多，但 **Cubism SDK 的商用授权需单独确认**（本报告未核实条款，属于实施前必查项）。

**必要说明**：走 B 就意味着形象从"你录像里的真人"变成"动画角色"。这对教学产品是**产品定位变化**，不是纯技术优化。请确认可接受。

### 2.3 路线 C 的参考实现与真实门槛

**【推断】** 公开资料显示这类方案在 8 GB 上"可玩"：

- [EchoMimic 8 GB 部署实战记录](https://laojin.blog/blog/20260324_echomimic_deploy_guide)
- [EchoMimicV2-ComfyUI](https://raw.githubusercontent.com/AIFSH/EchoMimicV2-ComfyUI/main/README.md)（社区称 6 步迭代、8 GB 显存可玩）
- InfiniteTalk（社区称 8 GB 可玩、支持无限时长）

**但这些"可玩"都建立在"能出片"的语义上。** 需要在 PoC 中实测的是**每秒生成帧数**，而不是"能否跑通"。这是本报告最重要的未验证项。

## 三、推荐方案

### 第一步（建议立即做）：真人动作帧序列 + 内容驱动的动作切换

**做什么**

1. 制作 4–8 套肢体动作帧序列（例如：强调手势、举例手势、翻页手势、思考姿态、指向屏幕）。素材来源可以是重新录制一段带这些动作的视频，再按与现有 150 帧同规格切帧（538×1080）。
   - **【实测】2026-10-14 已产出第一套**：未走真人录制，改用**图生视频**（单帧 → 5 秒「保持人物外观、双手在身前自然比划讲解」的视频）→ `genavatar` 一键转成素材（121 帧）。链路见 [`single-image-motion-research.md`](./single-image-motion-research.md) §5.2 的通路 B。**素材获取不需要讲师出镜**，这是相对本报告原始建议的实质改进。
   - **规格事实**：`genavatar` 产出的素材单帧尺寸**未必**与现有素材一致（实测 536×1080 vs 538×1080），因此实现必须在加载时归一化，否则会中途改变推流分辨率。
2. ~~用现有 `customopt` 机制加载这些序列~~ ❌ **实施时已否决**：`customopt` 是**抢占式整屏回放**——`base_asr.py:107` 在 `custom_audiotype > 1` 时优先吐自定义音频，只能"停下说话、放一段动作"，**做不到边说边动**。
   - **实际做法**：**直接替换渲染所用的帧源**（把 `frame_list_cycle`/`face_list_cycle`/`coord_list_cycle` 这组三元组整体换掉），动作与语音时间线互不干扰。这也顺带否掉了专项调研里"必须做分层合成"的判断（见其 §五）。
   - **驱动的扩展**：把动作的触发从"固定音频类型"改为**由讲稿内容驱动**——讲稿里用 `[GESTURE:<id>]` 标签指定某一段做哪个动作。
3. 讲课时的切换时机绑定到**段落边界**（与 `[PPT:N]` 分段同构），避免在句子中间跳变。✅ **已按此实现**：手势标签与 `[PPT:N]` 在同一层解析、同样作为段落边界；动作在段落**开始朗读**时触发，从手势第 0 帧起只完整播一遍，播完自动回默认姿态。

**为什么先做这一步**

- **零新增依赖、零新增硬件门槛、不动 CUDA**，在现有 25 fps 链路上直接成立。
- ~~复用已存在的 `customopt` 机制，改动面小。~~ → **实测不成立**：`customopt` 做不到"边说边动"（见上）。真实改动落在**取帧处**（帧源三元组 + 段落级触发），仍属不与 TTS/ASR/输出链路耦合的局部改动，风险可控——但比"复用 customopt"的预期要多改几处代码。
- 保留真人形象——不改变产品定位，不需要与教学团队确认风格变化。
- 能立刻回答"加了动作到底有没有变好"，为第二、三步提供判断依据。

**它的局限（必须如实告知）**

动作是**固定的几套**，只能靠映射规则粗略对应内容，**做不到"说到什么就做什么手势"的语义级对齐**。

### 第二步（真正可驱动）：并列新增可驱动 3D 角色链路

**做什么**：新增一条与现有真人管线**并列**的渲染链路（VRM + 骨骼动画），按 `avatar_id` 或新参数选择走哪条。现有真人链路完全不动。

**为什么并列而不是替换**：真人形象是本项目当前的差异化能力（讲师的真实面孔），直接换掉风险太高；并列则可以让用户按场景选——需要"像本人"用真人链路，需要"动作丰富"用角色链路。

**前置动作**：**【实测】`download.pytorch.org/whl/cu124/` 与 `download.pytorch.org/whl/cu121/` 均可达（739 ms / 573 ms，HTTP 200）**，阿里云 `mirrors.aliyun.com/pytorch-wheels/cu124/` 也可达。所以换 CUDA 版 torch 在网络上可行。换装后现有 wav2lip/MuseTalk 推理也会一并加速，是**独立收益**。

### 不建议：把视频生成作为实时对话链路

理由见 1.2。若确实需要"真人 + 真实肢体动作"的视频，建议做成**独立的预生成功能**（教师上传讲稿 → 离线生成视频 → 作为课件播放），而不是挂在实时对话链路上。这属于产品功能扩展，应单独立项。

## 六、明确未验证的假设

以下都是**推断**，不得当作事实进入实施：

1. 扩散式视频生成在本机 8 GB 上的**实际帧率**——未实测。报告里"达不到实时"是基于模型量级的推断。**（2026-10-14 增补：已收集到第三方实测数据，见 [`single-image-motion-research.md`](./single-image-motion-research.md) §3.2——结论不变，依据变强；本机复现仍为待办。）**
2. VRM 路线在浏览器端的**实际占用与帧率**——未实测。
3. **Live2D 的商用授权条款**——未核实，若倾向 Live2D 必须先确认。
4. ~~动作帧序列的**切帧规格能否与现有 150 帧严格对齐**~~ ✅ **已实测**：`genavatar` 一次产出 `full_imgs`/`face_imgs`/`coords.pkl` 三者索引严格对齐，帧数随源视频而定（实测 121 帧），**不要求恰好 150**。但**单帧尺寸会不一致**（536×1080 vs 538×1080），必须在加载时归一化，否则中途换帧源会改变推流分辨率。
5. ~~`customopt` 机制能否承受"频繁切换序列"而不产生**显存/内存抖动**~~ → **已不适用**：该机制被否决（见 §三 第一步）。**替代风险**：帧源素材常驻内存，单套约 210 MB（121 帧 × 536×1080），多套线性增长。设计上以"按需加载 + 缓存上限 2 套"约束，**内存实测仍待真机确认**。
