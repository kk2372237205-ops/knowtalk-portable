## 一、结论速览

1. **"单图"改变的是素材获取成本，不是渲染方式。** 现有管线（`full_imgs` 循环 + wav2lip 贴嘴）对素材的技术要求不变，单图只是让素材的来源从「录一段真人视频」变成「生成一段视频」。
2. **实时不可得。** 最自然的方案（Wan2.2-S2V-14B / 阿里 Live Avatar / 腾讯 HunyuanVideo-Avatar）要么需要 80 GB 单卡，要么是分钟级生成；8 GB 能跑的方案（InfiniteTalk / EchoMimicV2 / Wan2.2-Animate）也全是**离线出片**量级。**【推断】** 因此"肢体摆动"必须走"预生成素材"路径，与实时对话链路解耦。
3. **自然度不取决于模型档次，取决于一件事：动作是不是跟着语音走。** 固定循环摆动 3–5 秒就会被看出周期，这是最常见的翻车点。详见 §二.1。
4. **生成侧不是障碍，真正要绕的是 `customopt`——而它已经绕开了。** `customopt` 是"抢占式整屏回放"：播放动作时会盖掉正在说的话（`base_asr.py:107` 优先吐自定义音频），**因此不能用它做"边说边摆手"**。替代做法是**直接替换渲染所用的帧源**——手势不过是另一组 `(frame_list, face_list, coord_list)`，换掉引用即可，**不需要分层合成**。详见 §五 的更正。

## 二、效果最自然的决定因素（按影响力排序）

### 2.1 动作必须由音频/语义驱动，不能是固定循环 ★最关键

观众识别"这是循环"只需要 3–5 秒，一旦识别出周期性，沉浸感立刻崩塌。**素材必须是音频驱动生成（InfiniteTalk / EchoMimicV2）或真人动作迁移（Wan2.2-Animate），而不是几段待机动画交替播放。**

这一判断有专门的学术支撑：该方向（co-speech gesture generation）的核心问题就是"动作该跟着节奏还是跟着语义"。

| 方案 | 解决方式 |
|---|---|
| DiffSHEG | 统一扩散 + 测试时 outpainting（FOPPAS），**可达 ~30 FPS 流式**，但输出是 3D SMPL-X 动作参数，不是像素 |
| EMAGE | 内容-节奏自注意力（CRA）显式区分"beat-aware"（跟节奏）与"semantic-aware"（跟语义）；4 个 VQ-VAE 分别编码脸/上身/手/下身，避免手指等高频动作被躯干动作"平均"掉 |

**【推断】** 这也是为什么"给现有数字人加几套待机摆动片段轮播"的做法观感提升有限——它只能提供"活着"的暗示，提供不了"在讲这个内容"的信息。

### 2.2 幅度宁可小，不可大

真人讲课的肢体幅度其实很小：头部微动（点头/侧头约 3–8 度）、呼吸起伏、偶尔的手势。**大多数模型生成不出自然的大手势，强行要求大幅度动作会得到扭曲的手臂或手指粘连。**

- InfiniteTalk 的宣传点正是这个尺度：**"肩膀随呼吸起伏""点头、侧头响应语义，不是机械循环"**。
- Wan2.2-Animate 已知缺陷：**精细手部动作（如竖无名指）会出现手指粘连**，需去掉加速 LoRA 或提高采样步数。

**做法**：生成时用提示词约束幅度（"轻微自然的身体摆动、不做大幅手势"），素材审核优先保留小幅度版本。

### 2.3 构图：半身固定机位，脸居中

- EchoMimicV2 明确**对未裁剪/全身图效果下降**，要求**肩部以上裁剪**，参考图会先被 center-pad 到 768×768。
- **【实测，2026-10-14 复核更正】** 现有 `data/avatars/Mr.Chen/full_imgs/` 是 **150 帧 × 538×1080（宽×高，竖构图）**，白底全身正面站姿、双手自然垂在身侧，第 0 帧与第 75 帧完全一致 —— **是静止循环，手一动不动**。此前"1080×538 半身横构图"的描述**有误**（把宽高写反，且误判为半身），已更正。
- **做法**：生成素材保持同规格与同构图，避免重采样引入模糊；参考图用正面、光线均匀、脸部居中的半身照。

### 2.4 循环接缝与相位对齐

- 素材首尾帧要对齐（生成整数个动作周期，或让模型以首帧为终点收敛），否则循环处跳变。
- **切换动作的时机必须绑在段落边界**（与现有 `[PPT:N]` 分段同构），绝不能在句子中间切。
- 说话段与动作段的相位要对齐，否则会出现"嘴在说、身体不在那个节拍上"的错位感。

### 2.5 长时段一致性

生成超过 5–10 秒的素材时，必须用防漂移机制，否则人物会逐渐变形：

- InfiniteTalk：**soft conditioning** —— 控制强度不固定，由"当前上下文与参考图的相似度"动态决定；长视频用分段 + 重叠帧拼接。
- Wan2.2-Animate：**temporal RoPE**（跨分辨率对齐帧序）+ `continue_motion`（把上一段末帧作为下一段的时间锚点）；分段拼接时**所有子图的随机种子必须一致**。

## 三、方案对比

### 3.1 输入形态分类

| 类别 | 输入 | 代表 | 是否符合"只上传一张图" |
|---|---|---|---|
| 音频驱动 | 单图 + 音频 | InfiniteTalk、EchoMimicV2、Wan2.2-S2V、HunyuanVideo-Avatar | ✅ 完全符合（音频来自讲稿/TTS，用户本来就有） |
| 动作迁移 | 单图 + **驱动视频** | Wan2.2-Animate、Animate Anyone 系 | ⚠️ 需额外一段动作参考视频（可一次准备、长期复用） |

## 四、落地架构：离线生成 + 运行时回放

```
┌─ 离线，一次性 ─────────────────────────────────────────┐
│  单图 ──> InfiniteTalk / Wan2.2-Animate / EchoMimicV2   │
│           └─> 生成动作素材片段（数秒~数十秒）             │
│                └─> 按现有规格切帧 538×1080              │
│                     └─> 写入 data/avatars/<id>/full_imgs │
└────────────────────────────────────────────────────────┘
                          ↓
┌─ 运行时，实时（现有管线，25 fps）───────────────────────┐
│  身体层：full_imgs 循环播帧  ← 观察到的"肢体摆动"        │
│  脸部层：wav2lip 实时重绘嘴部 → paste_back_frame 贴回    │
│  切换层：在段落边界按内容/状态切换不同动作素材            │
└────────────────────────────────────────────────────────┘
```

这个架构的价值：**对外表现仍是"实时数字人"**（嘴是实时生成的），只有肢体动作是预生成的。产品形态不变，`--fps 25` 的实时约束不受影响。

**为什么不让扩散模型直接介入实时链路**：见上游报告 §1.2——本项目的实时性是硬约束（固定 25 fps 输出、`chat` 实时对话、`/interrupt_talk` 插话打断），而扩散模型是秒级/帧。

## 五、`customopt` 是抢占式回放——因此不用它，改用替换帧源

**【实测】** 现有动作机制无法实现"边说话边摆手"：

| 位置 | 行为 |
|---|---|
| `avatars/base_avatar.py:219` `__loadcustom()` | 按 `audiotype` 预加载「图片序列 + 可选音频」 |
| `avatars/base_asr.py:107` | `custom_audiotype > 1` 时**优先吐自定义音频**，注释写明"优先播放完自定义动作，可以通过 interrupt 打断" |
| `avatars/base_avatar.py:508-516` | 静音分支播 `custom_img_cycle[audiotype]` 的帧序列 |

即 `customopt` 的语义是"**整屏替换成另一段预录视频（含它自己的配音）**"，是一次抢占。它能让数字人"停下来做一段动作"，但不能让数字人"一边说一边动"。

**那么"边说边动"靠什么实现？靠替换帧源，不靠分层合成：**

| 对比项 | `customopt`（抢占式） | 替换帧源（本方案，已选定） |
|---|---|---|
| 动作单元 | 整屏预录视频，自带配音 | 另一组 `(full_imgs, face_imgs, coords.pkl)` |
| 与语音的关系 | 抢占：盖掉正在说的话 | 并行：语音时间线完全不受影响 |
| 能否边说边动 | ❌ | ✅ |
| 嘴型 | 素材自带，不重绘 | 仍由 wav2lip 按当前音频实时重绘 |
| 加载机制 | `customopt` json 配置 | `data/avatars/{id}/gestures/{gid}/` 目录约定 |

原先设想的两件事，实测后各有着落：

1. **脸部贴回坐标要逐帧跟随** —— **【已实测：此前"静态 bbox"的判断有误，此处更正】** `coords.pkl` **不是静态框，而是逐帧的**：`avatars/wav2lip/genavatar.py:130-174` 对每一帧单独做人脸检测（`get_smoothened_boxes(T=5)` 做 5 帧平滑），产出与 `full_imgs` 一一对应的 150 条 `(y1, y2, x1, x2)`。运行时 `avatars/wav2lip_avatar.py:206,260` 的 `inference_batch` 用同一个 `mirror_index(length, index)` 取帧、取脸、取框，三者索引天然对齐。**所以"身体摆动导致脸在画面中位移"这件事，现有管线本来就能跟随**，前提是素材为"一整段连续视频抽出的帧"。唯一真实风险是**循环接缝**：末帧 → 首帧若头位差得较大，回放时会有可见跳变，靠素材本身首尾姿态接近来规避。
2. ~~**动作相位与说话时段要对齐。**~~ → **在"只播一遍"的语义下不再是问题**：手势不循环、不要求与语音节拍对齐，而是在段落边界触发一次、完整播一遍后自动回默认姿态。**仍然存在**的是"手势与内容不搭"——素材是固定的几套，做不到"说到什么就做什么手势"（要语义匹配需 LLM 参与，属另一个变更）。

**【实测】实施成本已确认**：既不走 `customopt`，也不做分层合成。改动集中在一处（取帧），但代价转移到了**并发安全**上，共三处必须处理——① `inference()` 的 `length` 目前在 while 循环**外**取一次（`base_avatar.py:340`），换帧源后不会生效；② 切换瞬间必然出现"旧索引 + 新帧源"，两套素材帧数不同（150 vs 121）就会越界；③ 帧源素材常驻内存（单套约 210 MB），需按需加载 + 缓存上限。详见变更 [`add-gesture-module`](../openspec/changes/add-gesture-module/design.md) 的 design.md。

### 5.1 素材可以不自制：项目已内建"上传视频 → 自动生成素材"通路

**【实测】** 截至核对日，**换一套素材不需要写任何脚本**——页面入口和后台转换都是现成的：

| 层 | 位置 | 作用 |
|---|---|---|
| 页面 | `web/avatar.html`（中文）/ `web/avatar-en.html` | 填 `avatar_id` + 选一个视频文件 → 提交 |
| 接口 | `POST /api/avatar/task`（`server/avatar_routes.py:106`） | 收 multipart，落盘到 `data/tmp/`，创建任务 |
| 调度 | `server/task_manager.py:101-113` | `model_type == "wav2lip"` → 调 `avatars.wav2lip.genavatar.generate_avatar`（也支持 `musetalk`；**`ultralight` 无分支，会报 Unsupported**） |
| 转换 | `avatars/wav2lip/genavatar.py::generate_avatar` | 抽帧 → 逐帧人脸检测 → 逐帧 bbox → 裁 256×256 `face_imgs` + 写 `coords.pkl`，一条龙产出全套素材 |

由此，"摆动素材"的来源有三条，**都不需要你自己制作**：

1. **现成视频（零门槛，推荐）** —— 任何带自然微动的说话人视频，页面上传即可变成素材。来源：公开数据集（如 HDTF）、素材站、商业 API 产出的成品视频。**须注意版权与肖像权**。
2. **商业 API 生成（花点钱）** —— HeyGen / D-ID / 可灵 / 即梦等，输入一张图 + 文案即输出主持人视频，下载后走上面同一条通路。等于把素材制作外包。
3. **完全不做视频（纯程序化）** —— 对现有 150 帧做仿射/网格变形，用正弦驱动头肩微动。零素材零成本，但只能小幅 2D 变形，做不了手臂摆动，收益低，**不推荐**。

**两个必须先满足的硬条件：**

- **身份一致性**：wav2lip 用该 avatar 自己的 `face_imgs` 重绘嘴部再贴回。**换素材 ＝ 换人**——想让现有 `Mr.Chen` 这个形象动起来，素材必须是 Mr.Chen 本人（或同一身份）的视频；用别人的视频会得到一个"长着别人脸"的数字人。
- **素材时长要克制**：`wav2lip_avatar.py:97` 的 `read_imgs` 会把全部帧**一次性读进内存**。150 帧（538×1080）约 249 MB；60 秒素材（1500 帧）约 2.5 GB，会显著吃内存。建议素材控制在**十几秒以内**，且首尾姿态接近以便无缝循环。
- **尺寸要与默认素材一致**（2026-10-14 实施时新增）：`genavatar` 产出的单帧尺寸取决于源视频（实测手势素材 **536×1080**，默认素材 **538×1080**）。运行时在会话中途换帧源会**改变推流分辨率**，导致编码器重建。因此实现必须在**加载阶段**把手势素材归一化到默认素材尺寸（`coords.pkl` 等比缩放），保证输出画面尺寸全程恒定。详见变更 [`add-gesture-module`](../openspec/changes/add-gesture-module/design.md) 的 D6。

### 5.2 手部动作：能不能不自制？

**先看清现状**：现有素材是**全身站姿、双手自然垂在身侧、150 帧完全静止**（第 0 帧与第 75 帧逐像素一致，见 §三）。所以"手部动作"在现有素材上**做不出来**——必须换素材。

**好消息：让手动起来，零管线改动。** `wav2lip_avatar.py:258-265` 的 `paste_back_frame` 取 `frame_list_cycle[idx].copy()` 作底图，只替换人脸那一小块；`base_avatar.py:403-405` 在说话时同样逐帧推进 `index % length`。**结论：`full_imgs` 里的手怎么动，输出画面里的手就怎么动——静音与说话都一样。**因此"边说边摆手"**不需要**分层合成，换素材即生效。（此前"必须做分层合成"的判断只针对 `customopt` 抢占机制，**不适用于直接替换 `full_imgs`**。）

**三条"动作不自制"的通路，差别在于「动作与身份是否解耦」：**

| 通路 | 动作从哪来 | 身份是谁 | 解耦 | 本机代价 |
|---|---|---|---|---|
| **A. 动作迁移**（Wan2.2-Animate 等） | **任意人的动作视频**（网上任取一段讲课/手势） | 目标人物**单张图** | ✅ 彻底解耦 | INT8 权重 7 GB；16 GB 卡出 5 秒需 6–9 分钟；**手指易粘连** |
| **B. 商业 API**（可灵 / 即梦 / HeyGen / D-ID） | API 内置手势库或提示词 | 上传的单张图 | ✅ 基本解耦 | 花钱、数据外发、动作可控性有限 |
| **C. 现成视频上传**（`web/avatar.html`） | 视频里的人自带 | **必须是同一人** | ❌ 绑死 | 约等于零 |

**关键限制（最容易误判）**：通路 C 里动作与身份**不可能解耦**——`genavatar` 是按整段视频重建 avatar，`full_imgs` 是完整画面（含身体、衣服、手）。"拿别人的手 + 配 Mr.Chen 的脸"做不到：wav2lip 只在脸上贴嘴，**不会换身体**。想解耦只能用 A。

**手部特有的四个约束（比"身体微动"苛刻得多）：**

1. **手必须完整入镜。** 现有是全身竖构图、手在画面内 ✓；但若为满足 wav2lip 的"近景大脸"要求改成半身近景，手就会出画——**"嘴清晰"与"手可见"在取景上互相挤压**，这是必须先定的取舍。
2. **小脸问题仍在。** 当前脸框仅 **127×170 px**（占画面高 16%），与历史教训（"1080p 里 170px 小脸拉方必失败"）完全吻合。若只换手部动作素材、不改成近景，嘴部质量不会改善。
3. **循环接缝对手更敏感。** 手位移幅度远大于头部，末帧→首帧的跳变会非常显眼。要求素材自身周期完整、首尾姿态一致。
4. **帧数上限。** 一个像样的手势周期至少 3–5 秒；150 帧 @25fps = 6 秒，勉强一个循环。要多个不重复的动作就得加长，但内存约束在十几秒量级（见 §5.1）。

**推荐**：先走 **B** —— 拿一张 Mr.Chen 的图 + 提示"双手自然比划讲解"，产 5–10 秒视频后经 `web/avatar.html` 上传，看观感。零本地算力、零出镜、成本几块钱，且同时验证"换素材即让手动起来"与"循环接缝是否可接受"。若追求动作自然度，再上 **A**。

> ✅ **2026-10-14 已按此执行**：图生视频产出 5 秒「双手在身前比划讲解」，`genavatar` 转为 121 帧素材。结果见本报告 §六 P9 与项目日志；素材已登记为手势模块的第一套手势。

**上游报告的 P2（真人素材基线）也已被替代**：图生视频产出的素材同时充当了两者——它既是第一套可用的动作素材，也是"换素材能不能让手动起来"的实物证据。**代价是：本地生成路线（InfiniteTalk）未被验证**；若将来要按内容自动生成动作，仍需回到 P5。

## 七、明确未验证的假设

以下均**未在本机验证**，不得当作事实进入实施：

1. **InfiniteTalk / EchoMimicV2 / Wan2.2-Animate 在本机 8 GB 上的实际帧率与可用性**——全部为【第三方】数据。§3.2 的所有速度数字都来自社区文章，未经复现。
2. **SoulX-FlashHead 是否真的驱动肢体**——宣传语是"实时图片数字人"与"上半身"，但其驱动维度（表情/口型 vs 身体）**来源不明且疑似自媒体转载**，与 InfiniteTalk 的宣传高度雷同，**存在营销夸大嫌疑，须实测后再引用**。
3. ~~生成素材的规格能否与现有 150 帧严格对齐~~ —— **已澄清**：`genavatar` 一次产出 `full_imgs` / `face_imgs` / `coords.pkl` 三者索引严格对齐，帧数随源视频长度而定，不要求恰好 150。
4. ~~人脸框能否从生成侧直接获得~~ —— **已澄清**：能。`genavatar.py:160-174` 逐帧写出 `coords.pkl`，无需额外接检测器。
5. **帧源素材的内存开销**——换帧源本身不增加 GPU 负载，但素材常驻内存（单套约 210 MB，121 帧 × 536×1080）。设计上以"按需加载 + 缓存上限 2 套"约束，**实际峰值内存未在真机测量**。
6. **Wan2.2-Animate 的 INT8 版本（7 GB）质量损失是否可接受**——公开资料称"有可见的角色保真度损失"，是否影响教学场景可用性未知。**未执行（P8 未做）**。
