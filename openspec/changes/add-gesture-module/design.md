# Design

## Context

动机见 `proposal.md`。实现必须贴合现有渲染管线，这里只列出决定方案的现状事实：

- **帧源是三件等长序列**：`LipReal` 从 `load_avatar(avatar_id)` 拿到 `(frame_list_cycle, face_list_cycle, coord_list_cycle)`，全部在 `__init__` 一次性读入内存（`avatars/wav2lip_avatar.py:86-102`）。说话时 `inference_batch` 用 `face_list_cycle[idx]` 推理、`paste_back_frame` 用 `frame_list_cycle[idx]` 做底图并按 `coord_list_cycle[idx]` 贴回；静音时 `process_frames` 直接输出 `frame_list_cycle[idx]`。
- **索引由 `index` 决定**：`inference()` 维护自增 `index`，说话分支用 `index % length`（`base_avatar.py:405`），静音分支用 `mirror_index(length, index)`。`length` 目前在 while 循环**外**取一次（`base_avatar.py:340`），换帧源后不会自动更新。
- **段落级指令已有成熟通道**：`server/routes.py::_parse_ppt_segments` 把 `[PPT:N]` 切成段，每段带 `slide_id`；`server/routes.py::human` 逐段 `put_msg_txt(seg_text, seg_datainfo)`；`datainfo` 附着到该段每个音频帧的 `userdata`；`base_asr.get_audio_frame` 检测变化标记段边界；`process_frames` 在段首（`userdata.status == 'start'`）执行切页（`base_avatar.py:487-499`）。手势只需复用这条通道，把"切页"换成"触发手势"。
- **每个会话是独立的 avatar 实例**：`app.py::build_avatar_session` 为每个 `sessionid` 深拷贝 opt 并构造一个 `BaseAvatar`，因此手势状态放在实例上即天然按会话隔离。
- **素材由 `genavatar` 产出**，三件套齐全但单帧尺寸随源视频而变（现有默认素材 538×1080，已产出的手势素材 536×1080）。
- **`customopt` 机制不可复用**：它在 `custom_audiotype > 1` 时优先吐自定义音频（`base_asr.py:107`），是"停下来说话前做动作"，且 `set_custom_state` 在 `custom_audio_index` 无对应 key 时静默返回（`base_avatar.py:326`），要求动作必须自带配音。

## Goals / Non-Goals

**Goals:**

- 讲稿中的 `[GESTURE:<id>]` 能在段首触发手势，只完整播一遍，之后自动回到默认素材
- 全程不改变语音时间线：不插静音、不截断、不改变段落顺序与切页时机
- 切换不阻塞渲染线程，画面不掉帧、不黑屏、输出分辨率不变
- 手势状态、缓存、播放进度按会话隔离
- 未使用手势标签的会话，行为与改动前逐帧一致

**Non-Goals:**

- 不做素材生成/上传界面（本轮只做"用"，素材由外部产出）
- 不做按语义自动选手势（LLM 意图识别）
- 不做身体层与嘴部层的分层合成
- 不改造或替代 `customopt` 抢占式动作机制
- 首版不做手势间的交叉淡入与动作混合

## Decisions

### D1：以"替换帧源"实现，而非复用 `customopt`

手势本质是"换一组 `(frame_list, face_list, coord_list)`"，与 `customopt` 的"抢占音频通道"是两回事。

- **选择**：在 `BaseAvatar` 内维护 `_active_frames/_active_faces/_active_coords` 三个引用，切换即改引用；`paste_back_frame`、静音分支、补帧分支全部改为从这三个引用取。
- **放弃的方案**：用 `set_audiotype` 触发动作——它要求动作自带配音、会打断正在朗读的语音，与"边说边动"矛盾。
- **理由**：改动集中在取帧处，不触碰 TTS、ASR、输出链路；且默认素材就是"永远激活的帧源"，无手势时 `_active_*` 恒等于默认三件套，行为零变化。

### D2：标签与 `[PPT:N]` 同一层解析，分段结果携带两个字段

新增统一分段函数，用联合正则匹配两类标签：

```
\[(?:PPT|slide):(\d+)\]        → slide_id
\[GESTURE:([A-Za-z0-9_.-]+)\]  → gesture（大小写不敏感）
```

- 两类标签都作为段落边界，行为与现有 `[PPT:N]` 一致（先后顺序即播放顺序）。
- 段结果从 `(text, slide_id)` 扩展为 `(text, slide_id, gesture)`。
- `_parse_ppt_segments` 保留为薄包装（只取前两个字段），既有调用点与测试不必改动。
- **手势不跨段继承**：段未带标签则 gesture 为 `None`。这与"只播一遍"是配套语义——每段想要动作就显式写标签，不会出现"一段触发后每段都在动"的意外。

### D3：触发时机沿用"音频段首"，播放进度与 `index` 解耦

`process_frames` 已经在段首拿到带 `status == 'start'` 的音频帧，此处触发手势最自然：切页与做动作在同一时刻发生，且已经在音频真正开始播放时才执行。

- **只播一遍的判定**用**独立计数器** `_gesture_frames_played`，在 `inference()` 每产出一批帧时累加，达到手势帧数即恢复默认。
- **不**用 `index - start_index` 判定：`index` 会在"静音→说话"边界被重置（`base_avatar.py:389-390`），用它计数会算错。
- 静音期间手势照常推进帧序（规格要求静音时输出手势对应帧），因此计数器在静音与说话分支都要累加。

### D4：用"帧源代数"让推理线程重置索引

规格要求手势从第 0 帧开始。`index` 是 `inference()` 的局部变量，跨线程改不了，因此引入实例级代数：

```python
self._frame_source_gen = 0     # 每次切换帧源 +1
```

- `inference()` 每轮开头比较本地缓存的 `seen_gen`，不同则 `index = 0` 并更新。
- 切换、恢复默认、加载完成后的激活都走同一个 `_activate()`，统一 +1，避免遗漏。
- **理由**：比"轮询一个布尔标志再手动复位"更难漏；也让"加载完成时恰好中途激活"这一异步路径自然生效。

### D5：所有取帧统一取模，且 `length` 必须在循环内重取

- `inference()` 里的 `length` 移入 while 循环，保证换帧源后立刻生效。
- `paste_back_frame(idx)`、静音分支、补帧分支对三个列表的索引统一改为 `idx % len(list)`。
- **理由**：`index` 由推理线程计算、`idx` 经队列传给渲染线程，两者跨线程；切换瞬间"用旧 `idx` 索引新帧源"是必然出现的窗口，长度不同（150 vs 121）就会越界。取模把窗口内的最坏情况限制为"显示手势里的另一帧"，而不是抛异常打断渲染线程。

### D6：尺寸不一致时加载期归一化

推流分辨率在会话中途变化会导致编码器重建。因此约定手势素材单帧尺寸与默认素材一致；**加载时若不一致，把手势的 `full_imgs`/`face_imgs` 缩放到默认素材尺寸，`coords.pkl` 按同比例缩放**，并记一条警告。

- **理由**：已产出的手势素材是 536×1080、默认素材是 538×1080，二者必然不一致；与其要求素材侧对齐（容易漏），不如在加载处做一次幂等归一化，保证输出尺寸恒定。

### D7：后台加载 + 受理阶段预热

- 触发时若目标手势未加载，起一个 daemon 线程读盘，**加载期间继续输出当前素材**，加载完成后由 `_activate()` 原子切换。首次触发因此可能晚几十到几百毫秒开始做动作，但画面不断流。
- `server/routes.py::human` 在 echo 模式校验通过后，对本次文本用到的手势发一次**预热**（同样后台加载）；TTS 合成通常比读盘慢，预热基本能让首次触发就赶上段首。
- **放弃的方案**：`__init__` 里预加载该形象全部手势——单套约 210 MB，形象手势一多就会线性吃内存。

### D8：缓存上限 2 套，LRU 淘汰

`OrderedDict` 按最近使用排序，超过 2 套淘汰最久未用的。会话被回收时随实例一起释放。

- **理由**：一套 121 帧 × 536×1080 约 210 MB，加上默认素材已占的约 250 MB，上限 2 套把单会话增量控制在 ~420 MB；LRU 保证"来回用两三个手势"的讲稿不会反复读盘。

### D9：校验放在受理阶段，不接受静默降级

`POST /human` 的 echo 模式在入队前校验所有手势标签：**逐个区分**该形象**可用**与**不可用**的手势。可用的照常下发给渲染层；不可用的 MUST 从该段的手势指令中摘除（该段按默认素材渲染，等同没有手势标签），并**记录一条警告 + 在响应里带上该警告**。

- **理由**：讲稿是一次性提交的长文本，如果只把出错的段落跳过，用户会在讲课时才发现某段没做动作，且无从定位。**因此关键是「立刻让用户知道」，而不是「让整篇停下来」**——换一个形象时讲稿里的手势标签对不上是常态（两个形象的手势集合可能互不相交），此时整篇报错等于数字人彻底不出声，用户看到的只是「连上了但不说话」，比少几个动作严重得多。
- **不静默降级**：警告 MUST 同时出现在服务端日志与响应体里，客户端 MUST 把它显示给用户。做到了这一点，「跳过不可用手势」与「整篇报错」在用户感知上没有区别，但前者还能把课讲完。
- 运行时的兜底降级仍然保留（素材可能在入队后被删除）：渲染层降级为默认素材 + 警告，不中断朗读。
- **放弃的方案**：受理阶段只要有一个手势不可用就整篇报错。这版在「预设讲稿自动播放」路径上尤其致命——展示页的预设播放是静默提交，服务端返回的业务错误会被前端丢掉，用户既拿不到错误也听不到声音。

### D10：接口与前端

- 新增 `GET /api/avatars/{avatar_id}/gestures`，返回 `data.gestures = [{id, label}, ...]`，顺序稳定（按 id 排序）。沿用 `server/avatar_routes.py` 现有的 `AVATAR_ID_PATTERN` 校验与 `json_ok`/`json_error` 风格。
- 前端在"预设文本"区加一行手势标签按钮，点击把 `[GESTURE:id]` 插入 `<textarea>` 光标处（复用现有幻灯片标签按钮的插入方式）；手势列表随形象下拉变化刷新；无可用手势时给出提示而不是空白。

## Risks / Trade-offs

- **切换瞬间姿态跳变** → 首帧与默认素材当前帧姿态不同就会看到"闪一下"。缓解：素材制作时要求首尾姿态接近（已产出的手势素材首尾脸框只差 5 px，基本可用）；切换只发生在段落边界；后续必要时在 `enable_transition` 那套过渡机制上加短交叉淡入。**已接受**：首版不做淡入。
- **手势与讲稿内容不匹配** → 只播一遍的语义让"一段一个动作"，长段落只在开头动一次；手势是固定素材，做不到与语义相关。**已接受**（用户明确选择只播一遍）。
- **单会话内存增量约 420 MB** → 由 D8 上限 2 套约束；若实测吃紧，把上限降到 1 套只是常量改动。
- **加载延迟导致动作晚开始** → 由 D7 的预热 + 不阻塞渲染缓解；最坏情况是首次触发时手势从半途开始，不影响朗读。
- **回滚时标签会被当普通文本朗读** → 代码回滚后手势标签不再被识别和清洗，`[GESTURE:...]` 会被念出来。缓解：回滚时同时移除 `gestures/` 目录并清掉讲稿里的手势标签（校验消失后不会再拦住这种情况，需人工确认）。
- **`length` 移入循环后每轮多一次 `len()`** → 可忽略；`len()` 是 O(1)。

## Migration Plan

1. 迁移素材：`data/avatars/Mr.Chen_gesture/` 的 `full_imgs`、`face_imgs`、`coords.pkl` 移到 `data/avatars/Mr.Chen/gestures/explain/`，并写入 `gesture.json`（`{"label": "讲解手势"}`）。迁移后 `/api/avatars` 不再列出 `Mr.Chen_gesture`。
2. 上线代码，重启主服务。
3. 验证：`GET /api/avatars/Mr.Chen/gestures` 返回 `explain`；提交带 `[GESTURE:explain]` 的讲稿能触发；提交不含标签的讲稿逐帧行为与改动前一致。
4. 回滚：还原代码后，删除 `Mr.Chen/gestures/`（或移回 `Mr.Chen_gesture`），并清理讲稿中的手势标签。

## Open Questions

- 手势与 `customopt` 抢占式动作在同一会话同时触发时的优先级——当前 `customopt` 无素材可用（`customopt` 为空、无动作素材目录），暂不定义；将来两者都启用时再定。
- 是否需要交叉淡入：取决于真机观感，spec 不约束过渡形式，可后续单独变更。
