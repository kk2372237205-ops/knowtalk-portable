# RAG 问答失败的可诊断化与资源可回收

## 问题

现场反馈：展示页问「python语法是什么？」，回的是「当前知识库未覆盖，无法基于 PDF 资料回答。」

这句话是**错的**。当时知识库里明明有 271 个片段、正是这份资料，检索完全命中。
真相是**问答服务出错了**，而前端把任何失败都一律说成「知识库没覆盖」。

### 根因一：前端把「服务失败」谎报成「资料未覆盖」

`web/knowtalk-chat.html::askRag` 的 `catch` 分支只有一句话：

```js
setReplyText('当前知识库未覆盖，无法基于 PDF 资料回答。');
```

网络失败、HTTP 500、Ollama 挂了、侧车没起——全都落到这一句。
于是「服务坏了」被说成「知识库里没有这个内容」，用户既拿不到原因，
也会以为资料没上传，排查方向完全跑偏。

更糟的是服务端那边：`rag_service/api.py` 的 `except` 只 `raise HTTPException(500, detail=str(exc))`，
而 `detail` 是 requests 原始异常（`500 Server Error: Internal Server Error for url: ...`），
**既不点名是哪个依赖、也不说怎么处置**。

### 根因二：8B 模型把整条链路挤垮（这才是 500 的来源）

本机是 16GB 内存 + RTX 4060 8GB 显存。Ollama 里的 `qwen3-gpu:8b` 一旦加载：

| 占用项 | 数值 |
|---|---|
| `llama-server` 进程私有内存 | **6.2 GB** |
| GPU 显存 | **4.6 GB** |

而同一台机器上还要跑：KnowTalking 主程序（torch + wav2lip + librosa ≈ 2GB 内存 / 1.2GB 显存）、
RAG 侧车（1.4GB）、WorkBuddy 本体（1.5GB）、浏览器。**三者不能同时常驻。**

实测到的两种崩法：

1. **08:21 主程序被挤死**：Ollama 占着 6.2GB 内存时，主程序 import 到
   `scipy.signal` 直接 `MemoryError` 退出；整机可用物理内存只剩 0.8GB。
2. **08:21 问答 500**：wav2lip 占着 1.2GB 显存时，8B 模型申请 4643.78 MiB 连续显存失败 →
   `cudaMalloc failed: out of memory` → Ollama `/api/chat` 返回 500 → 侧车 500 → 前端谎报。

Ollama 的 `keep_alive` 默认 5 分钟，**模型用完不会卸载**，等于长期霸占显存与内存。

## 方案

1. **Ollama 请求一律带 `keep_alive`**：嵌入与生成都用完即卸（`keep_alive=0`），
   让 8B 只在「正在回答问题」的那十几秒里占资源，平时把内存和显存还给主程序。
   代价是每次问答多一次冷加载（实测约 9s），对课堂问答完全可接受。
2. **`chat()` 要有和嵌入同等的错误处理**：识别 CUDA OOM 并给出**可操作**的中文提示
   （哪个模型、要多少显存、怎么释放），而不是抛一个 requests 原始异常。
3. **前端不得谎报**：服务失败与「资料未覆盖」必须区分开——
   失败要说「知识库服务暂时不可用」并带上原因，资料真的没覆盖才说「未涉及」。
4. **服务端 `detail` 必须可操作**：点名是哪个外部依赖、什么原因、怎么处置。

## 影响

- 课堂问答不再被 8B 模型把主程序挤死；主程序与侧车可以和 Ollama 和平共处。
- 失败时用户看到的是真话和处置办法，而不是「知识库没覆盖」这种误导。
- 不改变 `/rag/ask` 的成功响应结构；失败仍是 HTTP 500 + `detail`（规格原就如此），
  只是 `detail` 变得可读、前端不再把它说成别的意思。
- 每次问答会多一次模型冷加载（~9s）。
