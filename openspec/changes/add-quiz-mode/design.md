# Design

## Context

### 现有讲课链路的实测事实

| 事实 | 位置 |
|---|---|
| `/human` 受理后立即返回，**不等待朗读完成** | `openspec/specs/digital-human-api/spec.md`「文本驱动的 echo 模式」 |
| 讲稿按 `[PPT:N]` 标签切分为多段，每段携带自己的幻灯片 | `server/routes.py:37-70`、`routes.py:120-161` |
| 切页时机绑定在**该段音频开始播放时**，不是提交时 | `avatars/base_avatar.py:495-497`、`slide-material-management`「标签驱动的幻灯片切换时机」 |
| 段落文字直接进会话的 TTS 队列 | `routes.py` 调 `avatar_session.put_msg_txt()` |
| 前端靠**轮询**获知状态，没有服务端推送通道 | `web/index.html:757-796` 的 `speakPollTimer` 轮询 `/is_speaking`；全仓库未找到 datachannel/WebSocket 事件推送 |
| 客户端当前是**讲课的驱动方**：自己 `fetch('/human')` 逐段送讲稿 | `web/index.html:721`、`:811` |
| 当前幻灯片按会话隔离 | `utils/material_manager.py:17`、`:585-602` |

结论：**"停下来"不需要在朗读流程内部插入阻塞**。只要不再发送下一段，朗读自然结束、幻灯片自然停在当前页——这正是既有机制已经具备的性质。

### 本机环境约束

- 只有 CPU，无 GPU（`torch 2.14.0+cpu`、CUDA 不可用）。语音识别必须在 CPU 上可运行，延迟要如实说明。
- 对话 LLM 走 `llm-configuration` 已建立的设置体系（`utils/settings_store.py`），判分复用它，不新增一套 LLM 配置。
- 无外网到 `huggingface.co`（此前实测不可解析），模型需可放本地目录。

## Goals / Non-Goals

**Goals:**

- 让讲课能在任意指定或随机的位置停下来提问，并且**幻灯片与朗读同时停住**。
- 学员能用文字或语音作答，AI 判分并给出可朗读的反馈，然后继续讲课。
- 普通模式（现有连续讲授）**行为零变化**。
- 课堂链路不因新增口令校验而受阻。

**Non-Goals:**

- **不修改 `/human` 的契约**。提问编排另起一层，不往 `/humanaudio`、`/interrupt_talk`、`/is_speaking`、`/llm_status` 里塞提问逻辑。
- 不做多选题／填空题的自动批改结构（第一期是开放问答 + LLM 判分）。
- 不做实时流式语音识别（边说边出字）。学员按住说完、整段提交即可，与 CPU 环境更匹配。
- 不做多人同时作答与排名。
- 不为提问模式引入服务端推送通道（保持轮询，与既有风格一致）。
- 不把提问点写成讲稿里的标签。理由是那会修改 `digital-human-api` 的「幻灯片标签解析与清洗」与 `slide-material-management` 的「PPT 标签解析与页序兼容」两条既有要求，而提问点本身是"这次讲课怎么问"的编排参数，不是讲稿内容的一部分。

## Decisions

### 决策 1：提问编排做成独立一层，而不是在 `/human` 内部暂停

`/human` 的既有要求明确写着"受理后立即返回成功响应，MUST NOT 等待朗读完成"。若在它内部等待作答，要么违反该要求，要么必须给 `/human` 加一个"会阻塞"的分支并修改它的规格。两者都不划算。

改为：新增提问编排层，自己持有"这次讲课还剩哪些段、下一个提问点在哪"。它按需把段落送进会话的 TTS 队列——用的还是 `put_msg_txt` 这条既有通路，因此不需要动朗读实现。

**收益**：既有四条相关要求（两条在 `digital-human-api`、一条在 `slide-material-management`）一条都不用改，普通模式天然不受影响。

### 决策 2：用"不再发送下一段"来实现停下

到达提问点时停止投喂段落即可。正在朗读的那一句让它播完（避免话说到一半被硬切），此后没有新段落进入队列，朗读自然结束，`mat_mgr` 的当前幻灯片自然停在最后一段所属的页。

**备选与否决**：也可以主动 `flush_talk()` 立刻打断。否决理由：会砍掉半句话，听感上像是故障；而且 `flush_talk` 的语义是"用户插话打断"，被提问逻辑复用会让两条路径互相干扰。

### 决策 3：提问点配置是**请求级参数**，不是全局设置

提问点依赖具体讲稿与幻灯片，做成全局设置没有意义（换个课件就要改）。因此"候选范围、数量、选取方式、随机种子、幻灯片范围、超时时长"都放在发起讲课的请求里，并各有默认值。

**这样做还顺带避免了**去修改 `runtime-configuration` 的「各配置项的生效档位归属固定」——而该能力当前还只在未归档的 `add-runtime-settings` 里，主规格中没有它，写针对它的 MODIFIED 增量会指向一个不存在的能力。

### 决策 4：随机必须可复现

实现上用固定算法（候选位置先排序，再用种子驱动的确定性洗牌取前 N 个），**不使用** `random.sample` 依赖全局随机状态。理由：教师课后复盘"为什么这题在这个位置问"时，必须能重放同一次选取。

### 决策 5：题库与问答记录都放 `data/` 下的 JSON

与既有的 `data/settings/settings.json`、`data/materials/slides_config.json` 保持同一风格（原子写、宽容解析、损坏时保留原文件并回落默认）。`/data/` 已被忽略规则覆盖，题库与记录不会入库。

**备选与否决**：上 SQLite。否决理由：这个项目目前没有任何数据库依赖，题库规模是课堂级（几十到几百题），JSON 足够；引入数据库会带来迁移与备份问题，收益不成比例。

### 决策 6：判分复用既有对话 LLM 配置，失败必须降级

判分调用 `llm-configuration` 已建立的 `api_key`/`base_url`/`model`，不新增 LLM 配置项。判分请求用非流式、带超时，并要求模型返回结构化结论。

**降级路径**：LLM 不可用时记录作答原文、标记"判分未完成"、播一句中性的过渡语，然后继续推进。这是硬要求（见规格）：课堂上不能因为 API 抖一下就永久停在那里。

### 决策 7：语音识别用 faster-whisper，默认 `small`，并发上限 1

- 选 `faster-whisper` 而不是内置的那份 OpenAI Whisper 源码：前者在 CPU 上快一个量级，且不依赖 torch 的推理路径。
- 默认规格 `small`：`base` 对中文术语识别偏弱，`medium` 在纯 CPU 上单句延迟过高。文档里给出实测延迟区间与切换方法，`RAG`/模型目录可指向本地路径以支持离线。
- **并发上限 1**：CPU 上并发识别只会让所有请求一起变慢；超出即立刻拒绝并告知"正在忙"，比排队到超时体验更好。
- 模型按需加载、进程内复用，避免每次请求重新加载几百 MB。

### 决策 8：前端保持轮询，不引入推送

提问状态的获取走"轮询 `/api/quiz/status`"，与既有 `speakPollTimer` 轮询 `/is_speaking` 的风格一致。轮询间隔在等待作答阶段放慢（例如 1 秒），避免无谓请求。

**备选与否决**：引入 WebSocket/SSE 推送。否决理由：会新增一条与现有轮询并行的架构路径，而本项目当前的推送需求（提问状态、进度）频率很低，轮询完全够用；真要做推送，应是一次统一的架构变更，而不是塞进这个变更里。

### 决策 9：口令边界按"课堂面 vs 配置面"切开

| 面 | 接口 | 口令 |
|---|---|---|
| 课堂面（学员用） | 提问状态查询、文字作答、语音作答、跳过、语音转写 | **豁免** |
| 配置面（教师用） | 题库增删改查、自动出题、问答记录查询 | **受保护** |

这与 `rag-sidecar-control`「RAG 控制接口受访问口令约束」和 `session-control`「踢出接口受访问口令约束」的既有划法一致：各自能力声明自己的边界，不去改 `access-control` 的豁免清单。豁免的接口 MUST 只作用于请求指定的会话，不提供跨会话批量操作（已在规格中约束）。

### 决策 10：提问模式的启用粒度是"按会话"

发起一次提问式讲课时启用，只影响该会话；不设"全局模式开关"。理由：一台服务可能同时服务多个教室/会话，全局开关会让一个教室开提问模式把另一个教室也带上。

### 决策 11：题目与提问点的绑定方式——支持按幻灯片精确指定

提问点决定"在第几段之后问"，题目来源有两种，**绑定优先**：

1. 请求可给出一张「幻灯片编号 → 题目标识」的**绑定表**。被绑定的提问点 MUST 问指定的那道题，MUST NOT 被随机或固定间隔选取覆盖。
2. 未被绑定的提问点，才从未被占用的题目中按选取方式（随机／固定间隔）取。

绑定表在启动时整体校验：引用不存在的题目标识、绑定到不属于本次候选提问点的幻灯片、或同一道题被绑到多个幻灯片，一律以业务错误拒绝启动并**指明冲突项**，而不是静默忽略。理由：静默忽略会让教师以为"第 3 页一定问这题"，实际却没问，这种偏差在课堂上无法当场发现。

**为什么绑定表是"幻灯片 → 题目"而不是直接用题目自身的 `slide_id`**：同一道题在不同课件里可能归属不同知识点，用题目自带的 `slide_id` 做绑定会把"题目"和"它在某份讲稿里的位置"两件事混在一起。因此题目的 `slide_id` 只用于筛选与自动出题，**不参与绑定校验**——允许把第 1 页的复习题绑到第 5 页。

### 决策 12：提问点默认落在幻灯片边界

候选位置默认是"每个幻灯片对应的最后一个教学段之后"（即讲完一页算一个候选点）。理由：这是教学中提问最自然的位置，也让"随机几处"与"按页绑定题目"都有一致且清晰的语义——**一个候选点最多绑定一道题**。

## Risks / Trade-offs

- **[CPU 识别延迟影响课堂节奏]** → 默认 `small` 并限制并发；文档给出实测延迟；接口带超时；识别失败保留等待状态允许重答。若实测不可接受，退路是浏览器 Web Speech API（不占本机 CPU，但需联网且仅 Chrome/Edge 支持）。
- **[LLM 判分不稳定或不可用]** → 强制降级路径（记录 + 中性过渡语 + 继续），并把"是否降级"暴露在状态与记录里，便于课后复盘。
- **[判分质量]** → 依赖教师填写的评判要点；题库新增时要求参考答案必填，并在文档中说明"评判要点写得越具体，判分越稳"。
- **[提问点选取与讲稿结构耦合]** → 候选位置来自讲稿分段，因此讲稿必须带 `[PPT:N]` 标签才能得到幻灯片边界。无标签的讲稿退化为按段落边界选点，行为需在文档中写明。
- **[新增依赖]** → `faster-whisper` 会拉入 `ctranslate2` 等包，与 `torch` 共存需验证；首次使用还要下模型。这两点都必须实测后在文档中给出结论，不能只写"应该可以"。
- **[等待作答把会话挂住]** → 必须有超时与跳过（已作为要求写入规格），否则一次忘答会让整个会话停死。

## Migration Plan

1. 先落题库与记录存储（含损坏回退），再落提问编排状态机。
2. 编排层挂在既有 `put_msg_txt` + `mat_mgr.set_current_slide` 通路上，普通模式路径不动。
3. 加语音转写：先只支持文字作答跑通全流程，再接语音。
4. 前端加提问卡片与模式开关，仅在提问模式下显示。
5. 端到端验证：普通模式回归（讲课时序与切页时机不变）+ 提问模式全流程 + 降级路径 + 口令边界。
6. 文档：README 增加提问模式一节（怎么配、怎么用、CPU 延迟量级与推荐模型规格）。

**回滚**：提问模式按会话启用，不启用即等同不存在；移除前端控件与路由注册即可完全回到变更前行为。题库与记录留在 `data/` 下，不影响运行。

## Open Questions

- 提问点是否要支持"答错就追问一次再继续"？（规格里只要求给出反馈后继续，未要求追问。）
- 问答记录是否需要导出成教师可读的形式（CSV/文档）？本变更只要求可查询。
- 语音作答是否需要"最长录音时长"的前端限制？后端已有体积上限，前端限制属于体验问题，可在实现时按实测延迟确定。

## 可行性实测结果（2026-10-13）

任务组 1 的实测结论。**注意：本变更规划时假设"本机只有 CPU"，该前提已被变更 `enable-cuda-runtime` 推翻**（已装 `torch 2.14.0+cu126`，GPU 可用）。以下是据此重新实测得到的事实。

### 依赖安装：有一个必须知道的陷阱

安装 `faster-whisper` 会拉入 `ctranslate2`、**`onnxruntime`（CPU 版）**、`tokenizers`。实测差异：

```
=> ctranslate2==4.8.3
=> faster-whisper==1.2.1
=> onnxruntime==1.23.2        ← 问题在这里
包数 142 -> 145
```

`onnxruntime`（CPU 版）与项目原有的 `onnxruntime-gpu 1.23.2` **提供同一个 `onnxruntime` 模块**，后安装者覆盖前者的文件。实测后果：

```
安装前：providers = ['TensorrtExecutionProvider', 'CUDAExecutionProvider', 'CPUExecutionProvider']
安装后：providers = ['AzureExecutionProvider', 'CPUExecutionProvider']   ← CUDA provider 消失
```

**修复方式**（已验证）：`pip install --force-reinstall --no-deps onnxruntime-gpu==1.23.2`，之后 CUDA provider 恢复。`--no-deps` 是必要的，否则会连带重装 numpy 等。

受影响的是 `avatars/ultralight/`（`pfld_mobileone.py:309`、`unet.py:243` 用 onnxruntime 做推理与校验）。这也是 `enable-cuda-runtime` 新增的「GPU 加速依赖的构建变体必须被声明并可校验」这条要求要覆盖的情形——**装一个 CPU 依赖就能悄悄换掉 GPU 能力**。

### 模型离线加载（任务 1.2）

下载 `Systran/faster-whisper-small` 到 `D:\models\faster-whisper-small`（461.1 MB）。

- 来源 `hf-mirror.com`；`huggingface.co` 在本机超时不可达。
- **单连接仅 0.72 MB/s**（461 MB 需约 10 分钟）；改用 curl 并行分块（8 线程 × 16 MB）后 **6.51 MB/s**，70.8 秒完成，大小逐字节一致。urllib 会被重定向目标以 403 拒绝，必须用 curl。
- 该仓库**没有** `preprocessor_config.json`，属正常。

**离线语义已验证**：把 `HF_ENDPOINT` 指向不可达地址 `http://127.0.0.1:9` 并设 `HF_HUB_OFFLINE=1`，模型仍从本地目录成功加载并完成转写。

### CPU 延迟与识别质量（任务 1.3）

测试音频是 Windows SAPI（Microsoft Huihui）**离线合成**的中文语音，文本已知可作标准答案。**这是合成语音而非真人录音，因此质量结论只能作参考，延迟结论有效。**

**实测延迟随机器状态波动明显**，同一段音频在不同时间测出的结果相差近 2 倍，因此这里给区间而不是单一数字：

| 音频 | 一次测量（机器较空闲） | 另一次测量（同机同时段） | RTF 区间 |
|---|---|---|---|
| 4.98 s | 1.59 s | 2.96 s | 0.32 – 0.59 |
| 6.58 s | 1.74 s | 3.14 s | 0.26 – 0.48 |

**结论：CPU(int8) 的 RTF 落在 0.26–0.59 区间，约 1.7–3.8 倍实时。** 一段 5 秒的学员回答约 1.6–3.0 秒转完，对课堂问答够用。模型加载约 1.2–3.0 秒（按需加载一次）。

> 上报延迟时**必须给区间或说明波动**，不要只写一个好看的单点数字——这台机器上同一份输入两次测量能差 1.7 倍。

**识别质量：内容 100% 正确，但默认输出简体/繁体不对。**

| 标准答案 | 无 prompt 的识别结果 |
|---|---|
| 同学们好，今天我们学习铁路客流量统计。 | 同學們好,今天我們學習鐵路客流量統計。 |
| 接下来请看第三页，这里展示了各个站点的日均客流量对比。 | 接下來請看第三頁,這裡展示了各個站點的日均客流量對比。 |

字词全对，但输出的是**繁体字**。这对中文课堂是错的。**修复方式已验证**：传 `initial_prompt="以下是普通话的句子。"` 即可得到简体输出：

| 变体 | 输出 | 含繁体 |
|---|---|---|
| 无 prompt | 同學們好,今天我們學習鐵路客流量統計。 | 是 |
| initial_prompt 简体 | 同学们好,今天我们学习铁路客流量统计。 | **否** |

**`initial_prompt` 的延迟代价已用 A/B 实测**（同一音频、同一模型、各 5 轮取中位数）：带提示 3.064 s vs 不带 2.983 s，**开销仅 2.7%**，可以忽略。**实现时 `initial_prompt` 是必需项，不是可选优化。**

> 早先只有两次单轮对比（1.58→1.75 s，约 10%），后来做了 5 轮中位数才确定真实开销只有 2.7%。这也说明单轮对比容易被噪声误导。

### GPU 转写：目前不可用（任务 1.4 的连带发现）

`ctranslate2` 能看到 CUDA 设备（`get_cuda_device_count() == 1`，支持 `float16`/`int8_float16`），但**实际转写失败**：

```
RuntimeError: Library cublas64_12.dll is not found or cannot be loaded
```

原因：CT2 与 torch 各走各的 CUDA 运行库，torch 自带的 `cublas64_12.dll` 在 `torch/lib/` 下，CT2 不去那里找。要用 GPU 转写需要额外安装 `nvidia-cublas-cu12` / `nvidia-cudnn-cu12` 之类的 pip 包并把它们的 `bin` 加入 DLL 搜索路径。

**决策：本变更不追求 GPU 转写**，理由是 CPU 的 RTF 0.26–0.59 已经满足课堂问答需求，而引入额外的 CUDA 运行库会增加部署复杂度（这与 `speech-to-text` 规格里「依赖或模型不可用时的失败必须可预期」的精神一致——少一个会静默失效的环节）。GPU 转写留作后续可选优化，届时需按 `enable-cuda-runtime` 的「构建变体必须被声明并可校验」要求一并处理。

**任务 1.4 的结论**：CPU 延迟可接受（RTF 0.26–0.59，约 1.7–3.8 倍实时），因此**不启用退路**（不需要改用 `base` 规格，也不需要浏览器 Web Speech API）。保留 `small` 作为默认规格。

### 另一个环境发现（与本变更无关，但影响课堂）

`edge_tts` 在本机返回 **403 Forbidden**（`speech.platform.bing.com` 拒绝握手），而 `--tts edgetts` 是本项目当前的默认 TTS。这不属于本变更范围，但**需要单独立项排查**：若 edgetts 持续不可用，课堂的语音播报会整体失效。已实测的替代方向：Windows SAPI（`Microsoft Huihui Desktop` 可用，离线）。
