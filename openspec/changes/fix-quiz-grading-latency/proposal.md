# 提问模式：判分提速与「提问即暂停」

## 问题

现场反馈两个问题：

1. **判分超级慢**。实测单次判分调用只要 ~0.9s（首次含 TLS 握手 ~3s），但学员体感是十几秒甚至卡住。
2. **提问时没有真正"让位"**：音频与幻灯片跟随仍在继续，学员来不及作答；播放按钮也不反映"现在是暂停着等你回答"。

## 根因

### 判分慢不是模型慢，是**整台服务被同步调用冻住**

`utils/quiz_grade.py::grade_answer` 与 `utils/speech_to_text.py::transcribe_audio`
都是同步阻塞调用（`openai` 的同步 client、faster-whisper 的 CPU 推理），
而它们分别被 `server/quiz_routes.py::quiz_answer` 与
`server/stt_routes.py::quiz_answer_audio` **直接在协程里调用**。

后果是同一个事件循环上的一切同时停摆：

- `aiortc` 的音视频收发要靠这个事件循环 → 判分期间数字人画面/声音卡住；
- `tick_quiz_sessions`（每 0.2s）停摆 → 讲稿推进停住；
- 展示页每 2s 的 `/api/quiz/status` 轮询排队 → 判分结果迟迟"看不到"；
- `/api/status`、`/api/current_slide` 等全部排队。

放大的两处细节：

- `OpenAI(timeout=45.0)` 用的是 SDK 默认 `max_retries=2`：一次超时最坏 45×3=135s，
  这期间整台服务一直冻着；
- 每次判分都 `new OpenAI(...)`，首次要重新做 TLS 握手（实测 +2s）。

语音作答路径更重：`transcribe_audio` 的 CPU 推理（RTF 0.26–0.59）同样在协程里同步跑，
一段 10s 语音先冻 3–6s，再冻判分 1–3s。

### 提问没有"让位"

展示页在 `in_quiz` 时只把自身的预设演讲标志清掉（`stopPresentationForQuiz`），
既不切断 WebRTC 音频，也不冻结 `/api/current_slide` 的幻灯片跟随。
于是提问点之后仍可能听到残留朗读、幻灯片继续被服务端推着跳，
学员既没"安静"下来，也没有一个明确的"继续播放"入口。

## 方案

1. **把阻塞调用挪出事件循环**：新增 `server/blocking.py::run_blocking`，
   答题判分（文字/语音两条路径）与语音转写统一走线程池。
2. **给判分设上限并复用连接**：`max_retries=1`、`LLM_TIMEOUT=12s`、
   模块级缓存 client；每次判分记录耗时，便于下次一眼定位。
3. **题目呈现即暂停**：`stage` 变为 `asking` 的那一刻展示页就切断音频、冻结幻灯片
   跟随、播放按钮切为「继续播放」（不等念完题）；点击「继续播放」或完成作答后恢复。
   等待页码阶段不暂停——页码靠段落音频首帧推进，一停就永远等不到。

## 影响

- 判分/转写期间服务不再假死，音视频与轮询保持流畅；判分失败最多等一次重试即降级。
- 提问时课堂真正停下，学员有安静的作答环境，且随时能一键继续。
- 不改变任何对外接口的请求/响应结构；`/api/quiz/answer*` 仍是同步返回判分后阶段，
  只是不再独占事件循环。
