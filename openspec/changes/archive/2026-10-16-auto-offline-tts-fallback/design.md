# Design

## Context

### 实测到的默认状态

`data/settings/settings.json` 里只有 `access_token`，没有任何 TTS 配置，因此完全走内置默认：

```
config.py:54            --TTS_FALLBACK  默认 ''
settings_store.py:90    tts.fallback    默认 ''
settings_store.py:82    tts.engine      默认 edgetts（已不可用）
```

结果：默认配置 = 必然失败的主引擎 + 无兜底 = 整堂课无声。日志证据（同一会话，12 页讲稿）：

```
00:02:17,798 [TTS] 开始合成: slide_id=1, voice=zh-CN-YunjianNeural
00:02:21,788 ERROR edgetts 请求失败: 403   ← 单次失败等待约 4 秒
...
00:02:54,209 ERROR edgetts 请求失败: 403   ← slide 12，全段无一成功
```

### 现有回退机制的形状

`tts/base_tts.py` 已经有：`TTSSynthesisError`（失败可见）、`_ensure_fallback()`（懒加载备用引擎、同名与未注册配置被拒）、`_synthesize_with_fallback()`（至多回退一次，不成环）。

缺的只有两件事：**默认值没人配**，以及**每段都要重新等一次相同的失败**。

### 一个容易踩空的实现事实

`SettingsStore.apply_to_opt()` 只应用 `_is_explicit()` 为真的字段（设置文件或环境变量显式写过），内置默认值不覆盖任何东西。因此：

> **只改 `FIELD_SPECS` 里的 `default` 对实际运行毫无作用**——`opt.TTS_FALLBACK` 仍会是 `config.py` 的 `''`。

两处必须同时改，否则会得到"设置页显示 sapi 已启用、实际仍不回退"的假象。

## Goals / Non-Goals

**Goals:**

- 不做任何配置启动服务，主引擎不可用时课堂**仍然能出声**。
- 把"每段等一次失败"的累计代价压到常数级。
- 外部服务恢复后**自动**回到更好的音质，不需要人工干预。
- 短路不得让任何文本被丢弃。

**Non-Goals:**

- 不修 `edge-tts`（无法修，等上游）。
- 不改 `sapi` 引擎本身，也不追求它的音质。
- 不新增开关来调节短路阈值（阈值先按实测固定，见决策 3）。
- 不改任何 HTTP 接口与前端控件结构。

## Decisions

### 决策 1：两处默认值同时改，平台判据沿用既有的一处

- `config.py` 的 `--TTS_FALLBACK` 默认值改为平台判定的 `sapi`；
- `utils/settings_store.py` 的 `tts.fallback` 默认值用同一判据（`sys.platform.startswith("win")`），与 `tts/sapi.py::IS_WINDOWS` 一致。

**为什么不是"只写进设置文件"**：那样只对当前这台机器当前这份数据有效，换部署或重置设置就回到无声；默认值才是"开箱可用"的落点。已显式配置过的部署取值优先，不受影响。

**为什么非 Windows 不设默认**：`comtypes` 与 SAPI 都是 Windows 专有，在其它平台指向它只会制造一个必然失败的配置项，把"无兜底"变成"有兜底但必然失败"。

### 决策 2：短路状态放在 TTS 实例上，天然按会话隔离

`BaseTTS` 的实例生命周期就是一个会话（`build_avatar_session` 按会话创建），因此短路状态放在实例属性上即可满足"新会话必须重新尝试主引擎"，不需要额外的会话表。重连即新会话，即重新探测。

### 决策 3：阈值是"连续两次失败 + 备用接管成功"

```
主引擎成功            -> 连续失败计数归零
主引擎失败            -> 连续失败计数 +1，尝试备用引擎
备用引擎接管成功      -> 若计数 >= 2，进入短路
```

**为什么不是一次**：一次失败可能只是网络抖动。一次抖动就把整堂课降级成机械音，代价明显大于多等一次（约 4 秒）。取 2 是"一次存疑、两次即证实"。

**为什么要附加"备用接管成功"**：没有可用的替代路径时短路毫无意义——那只会让后续每段都直接失败。

### 决策 4：解除短路有两条路径

1. **备用引擎也失败**：短路的前提（"有一条能用的路"）不成立了，立即解除，让下一次请求重新探测主引擎；
2. **新会话**：状态随实例消失。

两条路径都记日志，使"什么时候短路、什么时候恢复尝试"在日志里可追。

### 决策 5：不把默认主引擎直接改成 `sapi`

虽然改一个默认值就能立刻出声，但那等于**永久放弃好音质**，且微软侧一旦恢复也没有任何机制切回去。保留 `edgetts` 为首选、`sapi` 为兜底，得到的是"尽力用好音色，坏的时候不至于无声"。

### 决策 6：不做启动期探针

理论上可以在会话建立时先探一次主引擎，把 4 秒代价挪到启动阶段。放弃的原因：

- 探针必须是**真实合成**才有意义（TLS 握手成功、403 在应用层，网络可达性探测无效），而真实合成会把音频帧推进下游，污染帧契约；
- 短路已经把代价压到"最多两次失败等待"，收益不足以承担这个复杂度。

## Risks / Trade-offs

- **[兜底生效时音质下降]** → 文档如实说明；设置页展示当前生效的备用引擎及其来源，使"为什么声音变了"可从界面解释而非只藏在日志里。
- **[短路掩盖主引擎的长期故障]** → 进入短路时记一次 WARNING（说明原因与影响），解除时也记一次；日志仍能看出故障持续区间。
- **[阈值取 2 的判断可能不适用于其它网络环境]** → 取值理由成文（决策 3），真实课堂数据可用于后续调整；不为此新增配置项。
- **[`sapi` 在此机器上不可能不可用]** → 若 `comtypes` 缺失或系统无中文语音，`_ensure_fallback()` 会报告并放弃回退，行为退化为变更前（明确报错、不发声），**不会比现在更差**。
- **[默认值变化影响其他部署]** → 只影响"从未显式配置过备用引擎"的部署；显式取值（含显式留空）优先。

## Migration Plan

1. `config.py`：`--TTS_FALLBACK` 默认值按平台判定。
2. `utils/settings_store.py`：`tts.fallback` 默认值按同一判据。
3. `tts/base_tts.py`：连续失败计数 + 短路 + 解除。
4. 单元测试：默认值（两处一致）、短路阈值、单次失败不短路、短路后文本仍被合成、备用失效解除短路、新会话重新尝试。
5. 端到端：真机跑一次 `edgetts` 失败 → `sapi` 接管的链路，确认音频帧产出与短路生效。
6. 文档：README 补开箱行为。

**数据迁移**：无需。设置文件格式不变，已有显式配置的部署行为不变。

**回滚**：把两处默认值改回空即可，其余逻辑不依赖它们。

## Open Questions

- 阈值 2 是否为最优？当前按"一次存疑、两次证实"定值，真实课堂数据可校验。
- 是否需要在设置页提供"重新探测主引擎"的手动按钮（在微软服务恢复但会话仍在进行时有用）？本次不做，短路已由新会话自动解除。
